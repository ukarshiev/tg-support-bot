# Route: Claude-оркестратор + Codex-исполнитель

Связка двух вендоров, перенесённая из PostEditBot (контракт там утверждён Владыкой
20.08.2026, дополнен 22.08 и 27.08.2026). Claude планирует, ревьюит и делает delivery;
Codex (GPT через `codex` CLI) критикует план и пишет код. Ценность — model diversity:
разные модели имеют разные слепые зоны.

Этот документ — источник для восстановления skill на новой машине. Сам skill в git не
попадает (`.claude/` в `.gitignore`).

## Контракт цикла

1. **Триаж**: лёгкие задачи — Claude сам или Opus-субагент (без цикла); средние и
   сложные — Codex-worker. Цель — баланс лимитов двух подписок.
2. **Предусловия**: чистое рабочее дерево; Codex и другие агенты не работают на одних
   файлах одновременно; ветка `tgsupbot-{N}-{slug}` от `main`, где `N` — Plane-задача.
3. **Консилиум по плану** (сложные задачи): Codex-reviewer критикует план read-only,
   максимум 2 круга. План показывается Владыке, если затронуты БД, deploy, внешние
   контракты или публичное поведение ботов.
4. **Build**: `codex exec -p worker --sandbox workspace-write`; доработки — через
   `codex exec resume <session-id>` (та же сессия, контекст сохраняется). Codex не
   выполняет git/docker/migrate/tinker/тесты/deploy — только пишет код, гоняет Pint и
   PHPStan.
5. **Review**: Claude читает diff сам, гоняет `.\scripts\project-tools.ps1 quality`.
   Замечания классифицируются: critical / major / minor(nit). Новый круг запускают
   только critical/major; nit'ы идут списком в отчёт. Стиль решают Pint, PHPStan
   level 6, `CLAUDE.md` и `rules/`, а не мнения моделей.
6. **Выход**: успех = у обеих моделей ноль critical/major. Лимит 3 круга; после 3-го
   без консенсуса — эскалация Владыке + skill `grilling` (/grill-me).
7. **Delivery**: только Claude. Commit `TGSUPBOT-{N} | описание` → merge в `main` →
   `git push origin main` → deploy `.\start-relaxaclub-windows-docker.ps1` → контроль
   сразу и через 2–3 часа → комментарий в Plane. Миграции только по процедуре
   `AGENTS.md` (дамп + явное подтверждение).
8. **Самостоятельность решений**: развилки scope и дизайна агент решает сам, если есть
   лучшая практика, аналог в кодовой базе или разумный дефолт; выбор фиксируется в
   плане строкой «Принято решение: X, потому что Y». Вопрос Владыке допустим только
   при одновременном выполнении трёх условий: решение необратимо портит данные или
   ослабляет безопасность; одинаково разумных вариантов несколько; выбор нельзя
   вывести из кода, документации или практик. Все самостоятельные решения собираются
   одним блоком «Принятые решения» в финальном отчёте. /grill-me — только после 3-го
   круга без консенсуса, не для сбора требований на старте.
9. **Дедлайн и контроль прогресса**: до запуска Codex оркестратор обязан оценить объём
   задачи, назначить дедлайн и поставить контроль. Запуск «вслепую, без срока»
   запрещён — см. ниже.

## Дедлайн Codex и контроль зависания (обязательно)

Повод (PostEditBot, 21.08.2026): запуск worker простоял 4 часа с пустым выводом и
нулём изменённых файлов. Оркестратор этого не заметил, потому что не назначил срок
и не следил.

**До запуска** оркестратор оценивает класс задачи и назначает дедлайн:

| Класс задачи | Ориентир | Жёсткий таймаут в команде |
| --- | --- | --- |
| 1 файл, правка без новой логики | 5–10 мин | 900 с |
| 2–3 файла с логикой + тесты | 15–25 мин | 1800 с |
| Многофайловая/архитектурная | 25–40 мин | 2400 с |

**Корневая причина «зависаний» (найдена 22.08.2026).** При фоновом запуске stdin
остаётся открытым, и `codex exec` печатает `Reading additional input from stdin...`,
после чего ждёт ввод, которого никогда не будет. Внешне это неотличимо от работы:
процесс жив, вывода нет, файлы не меняются. Лечится закрытием stdin:

```
timeout 1800 codex exec -p worker --sandbox workspace-write "<промпт>" < /dev/null > <лог> 2>&1
```

`< /dev/null` обязателен для любого неинтерактивного запуска.

**Обязательные условия запуска:**

1. Команда обёрнута в `timeout <секунды>` — процесс не может висеть вечно.
2. Вывод пишется напрямую в лог-файл, **без пайпа** `| tail` / `| head`: пайп копит
   вывод до завершения, и лог выглядит пустым даже у работающего агента.
3. Поставлен сторож, который следит за появлением изменений в рабочем дереве
   (`git status --short`), а не за размером лога.

**Признак настоящего зависания** — выполняются оба условия одновременно:
дедлайн класса задачи превышен И в рабочем дереве нет ни одного изменённого файла.
Пустой лог сам по себе признаком не является.

**Действия при зависании, по порядку:**

1. Остановить процесс (убедившись, что он свой — по времени старта; PostEditBot
   на этой же машине тоже запускает `codex.exe`).
2. Smoke-проверка профиля: `codex exec -p worker --sandbox read-only "Ответь ровно
   одним словом: ok" < /dev/null`. Ответ за секунды означает, что профиль исправен и
   дело в задаче, а не в инструменте.
3. Перезапустить с более узким промптом: одна задача вместо нескольких, меньше
   контекста.
4. Максимум 2 перезапуска. После второго — остановиться и доложить Владыке факты.
   Третий перезапуск «на удачу» запрещён.

Оркестратор не пишет «Codex работает», если не проверил факт работы: живость
процесса и наличие изменений в дереве.

## Как формулировать запрос к Codex (проверено 27.08.2026 в PostEditBot)

Главная причина «Codex тупит» — не модель, а промпт. Три развёрнутых запроса подряд
не дали вердикта вообще (агент уходил читать код, искал несуществующие утилиты и
упирался в дедлайн), а короткий точный вопрос по той же теме получил ответ за минуту
и поймал фатальную дыру в плане, которую не увидели ни оркестратор, ни Opus-исполнители.

### Что не работает

- простыня контекста на экран плюс 4–6 вопросов разом — агент начинает исследование;
- открытая формулировка «оцени варианты, найди причины, предложи решение»;
- отсутствие ограничения на чтение — весь бюджет уходит на чтение файлов и graphify.

### Что работает

- **один вопрос за раз**; нужно три — три отдельных запуска;
- **факты давать в промпте**, а не заставлять искать;
- **явно ограничить чтение**: «не читай код и не ищи в интернете, ответь из своих
  знаний» либо «максимум 3 файла точечно»;
- **задать формат и объём ответа**: «максимум 7 строк вида `<проблема> -> <последствие>`»,
  «последняя строка: ВЕРДИКТ: план рабочий / нерабочий, потому что …»;
- **отдавать готовый план на критику**, а не заказывать исследование.

### Шаблон

```
Не читай код и не ищи в интернете. Ответь из своих знаний, коротко.
<ситуация в 2-3 строках>
<план в 4-6 строках>
Вопрос один: <ровно один вопрос>
Ответь строго так, максимум N строк: <формат>
В конце одной строкой: <вердикт>
```

Эмпирика по времени: короткий запрос с ограничением чтения укладывается в 1–3 минуты,
развёрнутое исследование не укладывается и в 15 минут.

## Известные дефекты инструмента (codex-cli 0.144.1)

- `codex exec resume --last` падает: `thread/list response decode error: AbsolutePathBuf
  deserialized without a base path`. Правка при этом НЕ вносится (выход 0, но работы
  нет — проверять `git status`).
- Обход: возобновлять по явному session id — `codex exec resume <uuid> "<промпт>"`.
  Id берётся из последнего rollout-файла:
  `find ~/.codex/sessions -name "*.jsonl" -newermt '-3 hours' | xargs ls -t | head -1`,
  затем `head -1 <файл> | grep -oE '"id":"[a-f0-9-]{36}"'`.
- `codex exec` **буферизует вывод до завершения**: пока агент работает, лог пуст.
  Проверять живость процесса (`wmic process where "name='codex.exe'" get
  ProcessId,CreationDate`), а не размер файла.

## Восстановление на новой машине

1. `npm install -g @openai/codex`, затем `codex login` (ChatGPT-аккаунт).
2. Создать `~/.codex/worker.config.toml`: `model = "<актуальная модель>"` +
   `model_reasoning_effort = "medium"`.
3. Создать `~/.codex/reviewer.config.toml`: та же модель + `model_reasoning_effort = "xhigh"`.
4. Восстановить `.claude/skills/route/SKILL.md` по контракту из этого документа.
5. Проверить: `codex login status` → «Logged in», smoke-запрос из раздела про зависания.

Имена моделей живут только в двух профиль-файлах: при выходе новой модели меняется одна
строка, skill и этот контракт не трогаются. Глобальный `~/.codex/config.toml` не изменять.
