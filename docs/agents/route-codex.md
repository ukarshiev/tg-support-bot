# Route: Claude-оркестратор + Codex-исполнитель

Этот документ — источник для восстановления skill на новой машине. Сам skill в git не

## Контракт цикла

1. **Триаж**: мелочь — Claude сам (без цикла); пакет однотипной механики — `luna` или
   субагент Sonnet по остатку лимита; код, тесты, диагностика, ТЗ — `worker`; экспертиза
   и высокий риск — `astra`. Цель — баланс лимитов двух подписок. Подробно — раздел
   «Выбор модели Codex по признакам задачи».
2. **Предусловия**: чистое рабочее дерево; Codex и другие агенты не работают на одних
   файлах одновременно; ветка `tgsupbot-{N}-{slug}` от `main`, где `N` — Plane-задача.
3. **Консилиум по плану** (сложные задачи): Codex-astra read-only критикует план и
   предлагает решение по каждому пункту; до 3 кругов на `medium`, затем до 6 на `high`.
   План показывается Владыке, если затронуты БД, deploy, внешние контракты или публичное
   поведение ботов.
4. **Build**: `codex exec -p worker --sandbox workspace-write`; доработки — через
   `codex exec resume <session-id>` (та же сессия, контекст сохраняется). Codex не
   выполняет git/docker/migrate/tinker/тесты/deploy — только пишет код, гоняет Pint и
   PHPStan.
5. **Review**: Claude читает diff сам, гоняет `.\scripts\project-tools.ps1 quality`.
   Замечания классифицируются: critical / major / minor(nit). Новый круг запускают
   только critical/major; nit'ы идут списком в отчёт. Стиль решают Pint, PHPStan
   level 6, `CLAUDE.md` и `rules/`, а не мнения моделей.
6. **Выход**: успех = у обеих моделей ноль critical/major. Лимит 3 круга; после 3-го
   без консенсуса — эскалация Владыке + skill `grilling` (/grill-me).
7. **Delivery**: только Claude. Commit `TGSUPBOT-{N} | описание` → merge в `main` →
   `git push origin main` → deploy `.\deploy-proxmox.ps1` на Ubuntu-ВМ → контроль
   сразу и через 2–3 часа → комментарий в Plane. Миграции только по процедуре
   `AGENTS.md` (дамп + явное подтверждение).
8. **Самостоятельность решений**: развилки scope и дизайна агент решает сам, если есть
   лучшая практика, аналог в кодовой базе или разумный дефолт; выбор фиксируется в
   плане строкой «Принято решение: X, потому что Y». Вопрос Владыке допустим только
   при одновременном выполнении трёх условий: решение необратимо портит данные или
   ослабляет безопасность; одинаково разумных вариантов несколько; выбор нельзя
   вывести из кода, документации или практик. Все самостоятельные решения собираются
   одним блоком «Принятые решения» в финальном отчёте. /grill-me — только после 3-го
   круга без консенсуса, не для сбора требований на старте.
9. **Дедлайн и контроль прогресса**: до запуска Codex оркестратор обязан оценить объём
   задачи, назначить дедлайн и поставить контроль. Запуск «вслепую, без срока»
   запрещён — см. ниже.

## Дедлайн Codex и контроль зависания (обязательно)

Повод (PostEditBot, 21.08.2026): запуск worker простоял 4 часа с пустым выводом и
нулём изменённых файлов. Оркестратор этого не заметил, потому что не назначил срок
и не следил.

**До запуска** оркестратор оценивает класс задачи и назначает дедлайн:

| Класс задачи | Ориентир | Жёсткий таймаут в команде |
| --- | --- | --- |
| 1 файл, правка без новой логики | 5–10 мин | 900 с |
| 2–3 файла с логикой + тесты | 15–25 мин | 1800 с |
| Многофайловая/архитектурная | 25–40 мин | 2400 с |

**Корневая причина «зависаний» (найдена 22.08.2026).** При фоновом запуске stdin
остаётся открытым, и `codex exec` печатает `Reading additional input from stdin...`,
после чего ждёт ввод, которого никогда не будет. Внешне это неотличимо от работы:
процесс жив, вывода нет, файлы не меняются. Лечится закрытием stdin:

```
timeout 1800 codex exec -p worker --sandbox workspace-write "<промпт>" < /dev/null > <лог> 2>&1
```

`< /dev/null` обязателен для любого неинтерактивного запуска.

**Обязательные условия запуска:**

1. Команда обёрнута в `timeout <секунды>` — процесс не может висеть вечно.
2. Вывод пишется напрямую в лог-файл, **без пайпа** `| tail` / `| head`: пайп копит
   вывод до завершения, и лог выглядит пустым даже у работающего агента.
3. Поставлен сторож, который следит за появлением изменений в рабочем дереве
   (`git status --short`), а не за размером лога.

**Признак настоящего зависания** — выполняются оба условия одновременно:
дедлайн класса задачи превышен И в рабочем дереве нет ни одного изменённого файла.
Пустой лог сам по себе признаком не является.

**Проблема известна разработчикам Codex:**
[openai/codex#20919](https://github.com/openai/codex/issues/20919),
[#27019](https://github.com/openai/codex/issues/27019) — Codex ждёт EOF на stdin, даже когда
промпт передан аргументом. Встроенных таймаутов у `codex exec` нет — внешний `timeout`
обязателен.

**Вторая известная причина, фикса нет:**
[openai/codex#41984](https://github.com/openai/codex/issues/41984) — если внутренняя
git-команда завершается с ненулевым кодом, Codex печатает ошибку и никогда не закрывает
turn. В этом проекте Codex git-команды запрещены полностью; нужные данные git собирает
оркестратор и передаёт готовыми в промпте.

**Прогресс смотреть через `--json`.** С этим флагом stdout становится потоком JSON Lines
с событиями агента. Эвристики ниже остаются запасным вариантом для запусков без `--json`.

### Ранняя диагностика: критерии смерти процесса

Критерий «нет изменённых файлов» не работает для read-only задач. Признаки измерены в
PostEditBot 11.09.2026 на двух зависаниях и одном здоровом запуске. Срабатывание
**любого** означает смерть процесса.

| Признак | Порог | Измеренный факт |
| --- | --- | --- |
| Файл сессии не создан | 60 секунд | здоровый создаёт за секунды; зависший не создал за 52 минуты |
| CPU процесса | < 1 с при возрасте > 3 мин | здоровый: 7,4 с за минуту; зависшие: 0,1–0,2 с за 52 и 91 минуту |
| Файл сессии перестал расти | 5 минут | зависший остановился на 149 КБ и не сдвинулся за 91 минуту |

Файл сессии: `~/.codex/sessions/<год>/<месяц>/<день>/rollout-*.jsonl`.

**Сторож обязателен.** Сразу после фонового запуска ставится проверка, которая через
3 минуты смотрит CPU и рост файла сессии. При срабатывании — снять процесс немедленно и
перейти на следующую ступень лестницы.

### Лестница эскалации

| № | Ступень | Когда переходим сюда | Модель и усилие | Потолок |
| --- | --- | --- | --- | --- |
| 0 | Определить тип вопроса | всегда, до запуска | — | — |
| 1 | Штатный запуск | вопрос требует суждения | `worker`, medium | 10 мин |
| 2 | Переформулировать | ступень 1 зависла или ответ мимо | та же | 10 мин |
| 3 | Дробить на части | ступень 2 не помогла | та же | 10 мин на кусок |
| 4 | Снизить усилие | ступень 3 не помогла | `worker`, low | 10 мин |
| 5 | Сменить модель | ступень 4 не помогла | `astra`, medium | 10 мин |
| 6 | Делать самому | бюджет исчерпан или 5 не помог | — | — |

Общий бюджет — 30 минут на задачу суммарно по всем ступеням; исчерпан — сразу ступень 6.
Ступень 0: команда отвечает на вопрос о **факте**, модель — на вопрос о **смысле**.
Ступень 6: писать «вердикт модели не получен», свой результат и чем он ограничен;
выдавать собственную проверку за ответ модели запрещено.

**Действия при зависании, по порядку:**

1. Остановить процесс (убедившись, что он свой — по времени старта; PostEditBot
   на этой же машине тоже запускает `codex.exe`).
2. Smoke-проверка профиля: `codex exec -p worker --sandbox read-only "Ответь ровно
   одним словом: ok" < /dev/null`. Ответ за секунды означает, что профиль исправен и
   дело в задаче, а не в инструменте.
3. Перезапустить с более узким промптом: одна задача вместо нескольких, меньше
   контекста.
4. Максимум 2 перезапуска. После второго — остановиться и доложить Владыке факты.
   Третий перезапуск «на удачу» запрещён.

Оркестратор не пишет «Codex работает», если не проверил факт работы: живость
процесса и наличие изменений в дереве.

## Как формулировать запрос к Codex (проверено 27.08.2026 в PostEditBot)

Главная причина «Codex тупит» — не модель, а промпт. Три развёрнутых запроса подряд
не дали вердикта вообще (агент уходил читать код, искал несуществующие утилиты и
упирался в дедлайн), а короткий точный вопрос по той же теме получил ответ за минуту
и поймал фатальную дыру в плане, которую не увидели ни оркестратор, ни Opus-исполнители.

### Что не работает

- простыня контекста на экран плюс 4–6 вопросов разом — агент начинает исследование;
- открытая формулировка «оцени варианты, найди причины, предложи решение»;
- отсутствие ограничения на чтение — весь бюджет уходит на чтение файлов и graphify.

### Что работает

- **один вопрос за раз**; нужно три — три отдельных запуска;
- **факты давать в промпте**, а не заставлять искать;
- **явно ограничить чтение**: «не читай код и не ищи в интернете, ответь из своих
  знаний» либо «максимум 3 файла точечно»;
- **задать формат и объём ответа**: «максимум 7 строк вида `<проблема> -> <последствие>`»,
  «последняя строка: ВЕРДИКТ: план рабочий / нерабочий, потому что …»;
- **отдавать готовый план на критику**, а не заказывать исследование.

### Шаблон

```
Не читай код и не ищи в интернете. Ответь из своих знаний, коротко.
<ситуация в 2-3 строках>
<план в 4-6 строках>
Вопрос один: <ровно один вопрос>
Ответь строго так, максимум N строк: <формат>
В конце одной строкой: <вердикт>
```

Эмпирика по времени: короткий запрос с ограничением чтения укладывается в 1–3 минуты,
развёрнутое исследование не укладывается и в 15 минут.

## Известные дефекты инструмента

Версия codex-cli закреплена на **0.160.1** (проверено на этой машине 09.10.2026). В 0.161.0
песочница Windows не запускает ни одной команды (`helper_unknown_error: setup refresh had
errors`, регрессия openai/codex#51634). После любого обновления CLI обязательны два запуска
с реальной командой — `codex exec -p worker --sandbox read-only "Выполни: git log -1
--format=%h"` и то же с `--sandbox workspace-write`; в выводе должно быть `succeeded`.
Запрос «ответь одним словом» команд не запускает и сломанную песочницу не ловит. Ответ
«model is not supported when using Codex with a ChatGPT account» лечится обновлением CLI.

- `codex exec resume` **не наследует профиль** и не принимает `-p` и `--sandbox` (0.160.1,
  проверено 09.10.2026): без флагов сессия продолжается на модели и песочнице из глобального
  `~/.codex/config.toml` — круг консилиума ушёл на `gpt-6-sol` с `workspace-write` вместо
  `astra` и `read-only`. Продолжать только так:
  `M=$(grep -oE '^model = "[^"]+"' ~/.codex/astra.config.toml | cut -d'"' -f2)`, затем
  `codex exec resume <uuid> -m "$M" -c model_reasoning_effort="medium" -c sandbox_mode="read-only" "<промпт>"`
  (для `worker` — его профиль и `sandbox_mode="workspace-write"`). После запуска сверять
  строки `model:` и `sandbox:` в шапке лога.
- `codex exec resume --last` падал на 0.144.1: `thread/list response decode error:
  AbsolutePathBuf deserialized without a base path`. Правка при этом НЕ вносится (выход 0,
  но работы нет — проверять `git status`). На 0.160.1 не перепроверялось.
- Обход: возобновлять по явному session id — `codex exec resume <uuid> "<промпт>"`.
  Id берётся из последнего rollout-файла:
  `find ~/.codex/sessions -name "*.jsonl" -newermt '-3 hours' | xargs ls -t | head -1`,
  затем `head -1 <файл> | grep -oE '"id":"[a-f0-9-]{36}"'`.
- `codex exec` **буферизует вывод до завершения**: пока агент работает, лог пуст.
  Проверять живость процесса (`wmic process where "name='codex.exe'" get
  ProcessId,CreationDate`), а не размер файла.

## Восстановление на новой машине

1. `npm install -g @openai/codex@0.160.1`, затем `codex login` (ChatGPT-аккаунт).
2. Создать `~/.codex/worker.config.toml`: `model = "gpt-6.1-sol"` +
   `model_reasoning_effort = "medium"`.
3. Создать `~/.codex/astra.config.toml`: `model = "gpt-6-astra"` +
   `model_reasoning_effort = "medium"`; `~/.codex/luna.config.toml`: `model = "gpt-6-luna"` +
   `model_reasoning_effort = "medium"`.
4. Восстановить `.claude/skills/route/SKILL.md` по контракту из этого документа.
5. Проверить: `codex login status` → «Logged in», два запуска с реальной командой из
   раздела «Известные дефекты инструмента».

Имена моделей живут только в трёх профиль-файлах: при выходе новой модели меняется одна
строка, skill и этот контракт не трогаются. Глобальный `~/.codex/config.toml` не изменять.
Профиля `reviewer` больше нет: 09.10.2026 файла `~/.codex/reviewer.config.toml` на машине
не оказалось, его роль выполняет `astra`.

## Консилиум: «критикуй и предлагай», эскалация усилия

1. Любой запрос к Codex-рецензенту формулируется как «покритикуй И предложи решение по
   каждому пункту». Чистая критика без решений не принимается.
2. Если за 3 круга согласие не достигнуто, оркестратор поднимает усилие `astra` до `high`
   флагом `-c model_reasoning_effort=high` в той же сессии и продолжает до 6 кругов.
   Генерация кода остаётся на `worker`.
3. Каждый круг: Codex перечисляет дыры с решениями; оркестратор принимает или отклоняет
   каждую (отклонение — только продуктовым решением Владыки), формулирует принятые решения
   с конкретными значениями и возвращает следующим кругом. Выход: ответ «достаточно» или
   конец 6-го круга; остаточные риски перечисляются явно и утверждаются Владыкой.
4. Итоги кругов и финальный контракт фиксируются в задаче Plane.

Проверено в PostEditBot 05.09.2026: три контракта сошлись за 6 кругов, число дыр падало
19→12→8→4→2→0.

## Багфиксы только red → green

Исправление дефекта начинается с теста, воспроизводящего дефект; код пишется под этот
тест. Codex тесты не запускает. Оркестратор на приёмке снимает правку кода во временный
патч (`git diff -- <src> > <scratch>/fix.patch`, `git apply -R <scratch>/fix.patch`),
прогоняет новые тесты через `.\scripts\run-isolated-tests.ps1` (должны упасть), возвращает
код (`git apply <scratch>/fix.patch`, должны пройти). `git stash` не используется: стек
общий для всех worktree. Тест, который не падает на старом коде, не принимается.

## Выбор модели Codex по признакам задачи

Модель выбирает оркестратор по формальным признакам; выбор «на глаз» и самая сильная
модель «на всякий случай» запрещены (повод в PostEditBot 06.09.2026: 20 % суточного лимита
ушло на Astra за два часа).

### Три профиля

| Профиль | Модель | Effort | Для чего |
| --- | --- | --- | --- |
| `luna` | `gpt-6-luna` | medium | Извлечение фактов, классификация, выжимки, разбор логов по шаблону, текст по готовым фактам |
| `worker` | `gpt-6.1-sol` | medium | Код, тесты, обычная диагностика, реализация по ТЗ, написание ТЗ |
| `astra` | `gpt-6-astra` | medium | Экспертная оценка: консилиум, ревью планов и правил, тупики Sol, необратимые решения |

**Код дешёвой модели не поручать:** любая правка с логикой идёт на `worker`.
**Мелочь не отдавать Codex вообще:** единичную правку дешевле сделать оркестратором, когда
контекст уже загружен. `luna` вызывается на пакет однотипной работы, а не на одну строку.

### Механика: `luna` или Sonnet по остатку лимита

Пакет однотипной механики выполняет Codex `luna` (`codex exec -p luna`) либо субагент
Claude Sonnet 5.5 (`Agent`, `model: sonnet`, `effort: medium`). Исполнитель меняется только
когда одна из подписок заканчивается — недельного лимита осталось 20 % и меньше:

- Codex: `rate_limits.primary.used_percent` в самом свежем
  `~/.codex/sessions/<год>/<месяц>/<день>/rollout-*.jsonl` (окно 10080 минут);
- Claude: инструмент `get_usage`, строка «Weekly · all models»; пятичасовой лимит ≥ 90 % —
  Claude тоже считается заканчивающимся.

| Состояние лимитов | Исполнитель |
| --- | --- |
| Обе подписки в норме | `luna` |
| Заканчивается Codex | Sonnet 5.5 |
| Заканчивается Claude | `luna` |
| Заканчиваются обе | та, где остаток больше |
| Остаток узнать не удалось | `luna` |

В отчёте — одна строка: исполнитель и оба остатка.

### Признаки выбора

Главные критерии — **неопределённость решения, последствия ошибки и проверяемость
результата**. Число файлов — подсказка, а не критерий. Конфиги, регулярки и миграции не
считаются автоматически простыми.

- Решение однозначно, логики нет, результат проверяется механически → `luna` или Sonnet.
- Есть логика, тесты, реализация или диагностика → `worker`.
- Нужна независимая экспертиза, цена ошибки — инцидент, данные или безопасность → `astra`.
  Высокий риск подключает `astra` **сразу**, без требования трёх провалов. Для этого
  проекта высокий риск — боевая БД и миграции, deploy, потеря или дублирование сообщений,
  контракты `PlatformChannel` и External API.

### Effort — отдельная ось

Усилие поднимается **флагом в той же сессии** (`-c model_reasoning_effort=high`), а не
сменой профиля: смена профиля теряет контекст. После тяжёлого этапа вернуть `medium`.

- Поднимать до `high` заранее: несколько порядков конкурентных событий; противоречащие
  ограничения; доказательство сохранения инвариантов при миграции.
- Поднимать по результату: `medium` после контрпримера и одной коррекции снова нарушает
  тот же критерий — один ограниченный проход `high` с этим контрпримером.
- Не поднимать, когда не хватает логов, контракта, доступа или решения Владыки, либо сломан
  инструмент. Число файлов и уверенный тон модели триггерами не являются.
- `xhigh` — только после измеренного выигрыша над `high`. `max` и `ultra` из автовыбора
  исключены.

### Супер-консилиум: Astra + Fable (двухвендорный)

**Когда:** 3+ круга обычного консилиума без согласия; причина инцидента не найдена;
архитектурный выбор с необратимыми последствиями; прямая команда Владыки.

**Порядок — параллельно и вслепую, затем перекрёстно.** Последовательная передача якорит
вторую модель на чужой формулировке, и независимые слепые зоны исчезают.

1. Оркестратор собирает самодостаточный пакет фактов: симптом, что проверено, что
   исключено, релевантные файлы и логи, критерий решения. Секреты в пакет не попадают.
2. Круг 1: один и тот же пакет одновременно уходит `codex exec -p astra --sandbox
   read-only` и субагенту Claude Fable (`Agent`, `model: fable`). Ответы друг друга они
   не видят.
3. Оркестратор сводит: совпадения — высокая уверенность; расхождения — предмет круга 2.
4. Круг 2: каждой модели показывают вывод другой и просят критику **расхождений**.
5. Итог Владыке: согласованное, оставшиеся разногласия с позициями сторон, рекомендация
   оркестратора. Максимум 2 круга.

Режим дорогой. Запускать по явному признаку, а не «чтобы надёжнее».

### Резервный режим: работа без Codex

Триггер — фраза Владыки «резервный режим», «без Codex» или «кончились токены Codex».

| Роль | Кто вместо Codex |
| --- | --- |
| Мелочь и единичные правки | Оркестратор сам |
| Пакет однотипной механики | Субагент Sonnet (`Agent`, `model: sonnet`) |
| Код, тесты, реализация по ТЗ | Субагент Opus (`Agent`, `model: opus`, фоновый) |
| Экспертиза, консилиум, ревью плана | Субагент Fable (`Agent`, `model: fable`) |

Запреты для исполнителя те же, что для Codex. Контракт приёмки не меняется: оркестратор
читает diff сам, классификация critical/major/nit, лимит 3 круга, delivery только через
оркестратора. Выход из режима — по явной команде Владыки.

### Дополнительные правила

1. **Каскад с объективной проверкой.** Дешёвая модель считается справившейся только если
   прошёл формальный критерий: тесты зелёные, Pint и PHPStan чистые, diff только в
   разрешённых файлах. Промах — эскалация на ступень выше, а не повтор на той же модели.
2. **Курированный контекст для дешёвых моделей.** `luna` получает точные файлы и строки и
   ожидаемый результат. Задачу «найди сам» дешёвой модели не давать.
3. **Лимит Astra.** Не более двух запусков в сутки без согласования; третий и далее — только
   с явного согласия Владыки. Прямая просьба Владыки о консилиуме считается согласием на его
   круги. Профили общие с PostEditBot, поэтому запуски считаются по машине. При исчерпании
   лимита задача откладывается, а не спускается на слабую модель молча.
4. **«Думать» и «делать» разделены.** Дорогая модель пишет ТЗ и ревьюит (короткие вызовы),
   дешёвая исполняет по ТЗ (длинные вызовы).
5. **Без каскада в интерактиве.** Когда Владыка ждёт ответ в чате, сразу берётся нужная
   модель; каскад — только для фоновой работы.
6. **Запреты на окружение.** Исполнителю запрещены `composer install/update`, `npm ci`,
   `npm install`, любые изменения `vendor`, `node_modules` и lock-файлов, а также `git stash`.
   Если проверка не запускается — остановиться и доложить, не чинить окружение. Повод в
   PostEditBot 07.09.2026: пять параллельных исполнителей одновременно запустили `npm ci` и
   разрушили `node_modules`. Полный gate запускает только оркестратор, когда в дереве нет
   чужих незавершённых правок; он не пушит, пока хотя бы один исполнитель работает.
